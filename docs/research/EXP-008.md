## Plan (unchanged, ready to run)

On the encoder EXP-004 Run 2 selects (CROMA or DOFA):

| Step | Method | Notes |
|------|--------|-------|
| baseline | **frozen encoder + linear probe** (train only a linear head on frozen GAP features) | this is *not* LoRA and *not* fine-tuning |
| adapted | **LoRA / PEFT** — low-rank adapters inserted in the encoder, rank + target modules recorded | if LoRA training is too costly locally, fall back to a **2-layer MLP head** on frozen features and label it exactly that ("frozen features + MLP head", not "adaptation of the backbone") |
| eval | identical split, metric, and budget as the baseline | multilabel micro-F1 / mAP (BigEarthNet-v2) or per-class F1 (DFC2020) |
| report | baseline → adapted, **absolute + relative delta**, compute time, memory | all in this file, as a *SatQuery result* (number #3) |

Terminology is kept exact: **linear probe ≠ LoRA ≠ full fine-tuning ≠ instruction
tuning**.

## G6 Phase 6 — method definitions locked (so the run is unambiguous)

| Name | Exactly what is trained | What is frozen | Reported as |
|------|-------------------------|----------------|-------------|
| **linear probe** (baseline) | one `nn.Linear(768→C)` (or `1536→C` for DOFA-fused) on frozen GAP features | the **entire** encoder | "frozen encoder + linear probe" |
| **LoRA** (adapted) | low-rank adapters (`r`, `alpha`, target modules recorded) in the encoder attention/MLP; the linear head | encoder base weights | "LoRA adaptation of the backbone" |
| MLP-head fallback | a 2-layer MLP on frozen features (only if LoRA is too costly on the box) | the **entire** encoder | "frozen features + MLP head" — **explicitly not backbone adaptation** |

**A linear probe is never called fine-tuning.** The before→after number is only a
*SatQuery result* (#3) if the encoder itself was adapted (LoRA) — otherwise it is
"frozen-feature head comparison".

**Hyperparameters to record:** optimizer, lr, epochs/steps, batch size, LoRA
`r`/`alpha`/dropout/targets, seed, GPU, wall-clock, peak VRAM.

## Result (DONE 2026-09-02, G12 — `evaluation/reports/exp008_20260902T120050.json`)

CROMA, DFC2020 400 train / 200 eval, seed 20260902, CPU, 6 epochs, LoRA r=8 α=16
on the attention `to_qkv`/`to_q`/`to_k`/`to_v` Linear layers (**42 layers
wrapped, 811,008 trainable params = 0.4 % of CROMA's 194 M; 3.24 MB fp32
adapter**). Peak CPU RSS 1.51 GB. **No CUDA on the host → no VRAM figure.**

| arm | representation | macro-F1 | accuracy | infer s/patch |
|-----|----------------|:--------:|:--------:|:-------------:|
| 1 | optical-only (frozen) | 0.656 | 0.82 | 0.385 |
| 2 | fused optical+SAR (frozen) | 0.643 | 0.85 | 0.555 |
| **3** | **fused optical+SAR (LoRA-adapted)** | **0.704** | 0.835 | 0.378 |

- **adapted − frozen fused: +0.061 macro-F1** — clears the pre-registered
  **+0.03** adoption threshold.
- adapted − optical-only: +0.048.
- frozen fused − optical-only: **−0.014** — with a plain torch linear head +
  AdamW (6 epochs) the *frozen* fused arm did **not** beat optical-only here.
  (EXP-004 Run 2's `LogisticRegression` probe *did*: 0.793 vs 0.726. The head
  matters — EXP-008's 3 arms share one head so the *adapted vs frozen* delta is
  internally fair, but the absolute frozen numbers are not comparable across the
  two experiments.)
- Training loss fell to 0.15 → LoRA has capacity to overfit 400 patches. The
  held-out gain is real **in this run** but **not significance-tested** (n_eval =
  200; deltas were not bootstrapped).
- Inference cost of the adapted encoder ≈ the frozen encoder (0.378 vs 0.385
  s/patch) — LoRA adds negligible latency. LoRA params were **not persisted** in
  this run (`--save-adapter` added to the harness afterwards); a larger-split
  re-run persists the adapter.

## Decision (pre-registered rule applied)

**ADOPT the LoRA-adapted encoder as the adaptation method for capability E.**
The rule — "adopt iff (adapted − frozen fused) ≥ +0.03 macro-F1 **and** no
deployment blocker" — is met: **+0.061**, 0.8 M trainable params, 3.2 MB adapter,
CPU-runnable, no latency penalty. **Not** a full fine-tune.

**Deployment note:** production keeps the **frozen** CROMA encoder as the default
until this is confirmed on a larger split (full 986-patch validation, or the
5128-patch DFC2020 test ROIs) with bootstrapped deltas. Adoption here is a
*method* decision (LoRA is the E approach, and it works); flipping the production
default to the adapted encoder is gated on that confirmation. This is additive
(an opt-in `--lora-weights` load path), not an architecture change.
